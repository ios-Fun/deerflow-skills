## ⛔ 最高优先级硬约束（优先于本文件其他所有规则，不可协商）

1. 禁止跨设备查询：除目标实体本身及其直接挂载测点外，不得查询任何其他
   设备/系统的测点与数据，即使以"对照、排除、验证、确认系统原因"为名义
   也不允许。一旦判断需要系统级信息，立即停止取数，回复用户"该问题可能
   涉及其他设备/系统数据，如需确认请授权另行分析"。

2. 禁止主动深挖：本技能为单轮快速执行。满足以下任一情形，必须立即输出
   结论并停止调用任何工具，等待用户追问：
   - 用户问题属于"为什么 / 给结论 / 判断原因"类；
   - 已取得目标设备自身的关键测点数据；
   - 已给出第一层（一个）可能性判断。
   未经用户明确要求，不得以"严谨性、完整性"为由继续取数。

3. 结论单层：原因类问题只输出"最可能的一个原因 + 支撑证据 + 已排除项"，
   不再向下追因、不再罗列备选方案等用户挑选。

4. 批次兜底：每次回复计划发起多个工具调用时，先逐项核对实体归属；凡涉及
   目标设备以外实体的调用，整体取消该批，仅保留目标设备内的查询。

5. 反例（均属违规）：
   - 用户问"泵D出口压力为何升高"，却查询泵A/B/C运行状态或阀位；
   - 给出"疑似系统侧工况变化"后，又继续查询凝汽器/母管/并列泵数据；
   - 为"核对/排除"某参数而查询用户未提及设备的测点。


# Parameter Analysis

## 执行前实体校验

- 存在 `<user_enrichment>`：必须使用其中实体，多个设备时用 `ask_clarification` 确认。
- 不存在 `<user_enrichment>`：禁止自行猜测实体名称，中止并回复用户确认。

## 时间处理

遵循 `references/time-handling.md` 中的规则。

## 执行流程

### 1. 识别实体和分析目标
确定分析实体、类型、时间范围、待解决问题。

### 2. 获取相关测点
首先，确认`<user_enrichment>`包裹内容的`type`类型是什么，根据不同的类型，选在下述不同的逻辑去执行
- 实体为测点：直接使用。
- 实体为部件/设备/子系统/系统：调用 `get_tags_of_instance`。
  - 查询趋势/数值 → tagType 指定 `模拟量`
  - 查询开闭状态 → tagType 指定 `开关量`
- 不查询与目标无关的测点；不存在相关测点时立即终止。

### 3. 问题分析
严格将用户提问划分成下述的一类问题进行问题处理，不要将用户的提问内容理解成成多类问题的复合问题进行处理
- 开关量状态类 → 参考 `references/switch-analysis.md`
- 模拟量状态类 → 参考 `references/analog-analysis.md`
- 趋势变化类 → 参考 `references/trend-analysis.md`
- 异常原因类 → 参考 `references/fault-diagnosis.md`
- 超限/干预类 → 结合阈值判断，无阈值时只做相对判断

### 4. 趋势图输出
用户要求查看趋势或分析基于时间范围数据时，输出 `parameter_trend` 结构，协议见 `schemas/parameter-trend.md`。

## 分析原则
1. 单设备查询：只允许查询目标设备本身及其直接挂载测点，禁止跨设备查询，如询问A泵下测点情况，不可以查询到B泵下的测点。
2. 趋势优先：涉及“持续、升高、异常”等问题时，不能只看单点。
3. 关联分析：设备问题尽量结合多个相关参数判断。
4. 分层取数：统计初筛 → 原始数据详情。
5. 实体驱动：部件/设备/子系统/系统必须先获取下属测点。
6. 避免过度查询：不查询与用户问题无关的参数。
7. 不能臆断：无数据支撑时，不得编造参数值、阈值、异常原因或设备故障。
8. 证据不足时明确说明：只能判断参数异常时，不直接认定设备故障。
9. 数据优先：结论必须基于实际查询数据。
10. 工具限制：白名单外无法回答时，明确告知所需数据，不擅自调用其他接口。
11. 快速响应：该skill要求单次快速执行，不要因为为了深究问题所在一直深挖原因，每次可以根据用户输入给予一个可能性判断，不要一次性直接解决问题， 可在用户追问的情况下在慢慢补全数据。

## 输出规范
- 用户要求确认故障时，明确回答：**可确认 / 疑似 / 证据不足**，列出关键特征满足项数。
- 不得为验证目标测点实际值而无条件查询其他测点。
