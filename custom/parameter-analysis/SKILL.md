# Parameter Analysis

## 执行流程

### 执行前实体校验

本 Skill 基于已识别并确认的实体执行分析。
- 如果 message 中存在 `<user_enrichment>`：
  - 必须协同使用 `<user_enrichment>` 中提供的实体信息。
  - 不得使用用户原始问题中的同名或近似名称替换已识别实体。
  - 如果数据中包含有多个设备，调用`ask_clarification` 向用户确队分析哪个设备，options 应提供`<user_enrichment>`中的最相近的实例，后续流程均不再进行。
- 如果 message 中不存在 `<user_enrichment>`：
  - 禁止根据用户问题自行截取、拼接、猜测或生成实体名称。
  - 中止回答，回复用户未匹配到相关实体（部件、设备、系统、子系统），让用户重新确认下。

### 1. 识别实体和分析目标

根据用户问题及附带实体信息确定：
- 分析实体
- 实体类型
- 用户要求的时间范围
- 用户需要解决的问题

### 2. 获取相关测点

- 如果实体类型为 **测点**：直接使用该测点信息查询数据。
- 如果实体类型为 **部件、设备、子系统、系统**：调用 `get_tags_of_instance` 获取实体下属测点，然后根据用户问题筛选相关测点，需要注意，如过是问趋势，数值等信息，tagType需指定为`模拟量`，如果说查询测点是否开闭，测需要指定tagType为`开关量`。
- 如果当前测点不足以完成分析，无需查询与目标参数无关的测点。
- 禁止无差别查询实体下全部测点，也不得自行编造不存在的测点。
- **如果当前实体下不存在用户目标相关的测点，则立即终止；只有当前实体相关测点在现有数据不足时，才允许继续查询当前实体内的其他相关测点。**

### 3. 查询测点数据

根据分析目标选择查询方式：
- `get_tag_statistic_data`：作为参数状态判断的主要依据，用于获取实际值、估计值、严重度、异常数量等统计信息。
- `get_tag_values`：用于需要具体时间序列时的趋势分析、异常起始时间、持续变化及趋势图。
- `get_last_time_by_switch_name`：用于查询指定开关量的开闭情况，该方法会根因为传入的参数的差异，结果也会有所不同，1.当传递value，且startTime和endTime均不传递时，查询的是当该开关量等于该值的最新时间 2.当传递startTime和endTime，且value不传递时，查询的是该开关量在当前时间窗口内每次变动的时间戳。
数据使用原则：
- `get_tag_values` 返回的实际值就是测点实际运行值，不需要通过统计值、历史值或其他测点进行真实性验证。
- `get_tag_statistic_data` 用于判断该实际值所处的运行状态、异常程度及统计特征。
- `get_last_time_by_switch_name` 当需要查看某个开关量最后一次跳变的时候，仅传入value；当需要查看某个开关量再一段时间内的跳变情况，则传入startTime和endTime。
- 不得因为实际值看起来偏高、偏低、恒定或异常，就默认怀疑数据错误或继续进行数据真实性验证。
- 只有用户明确询问数据是否异常、是否失真、是否存在测点故障时，才进行数据质量或历史一致性分析。
查询策略：
- 统计数据初步判断 → 必要时查询原始数据进行趋势分析。

### 4. 参数聚类分析

不要逐个测点机械分析。根据用户问题将相关测点按照参数类别进行聚类：
- 温度类
- 振动类
- 电气类
- 压力/流量类
- 运行状态类
- 负荷/工况类
- 告警/保护类
先分析同类参数整体趋势，再结合不同类别参数之间的变化关系进行综合判断。
例如设备异常分析通常优先关注： 目标异常参数 + 相关温度参数 + 相关振动参数 + 电流/负荷 + 设备运行状态 + 报警/保护
实际查询哪些参数，由用户问题和已有测点信息决定，不要求每次全部查询。

### 5. 根据问题进行分析

#### 开关量状态类
针对“是否有断开，断开动作发生在几点，某时间段有无跳变情况”等问题：
- 优先根据`get_last_time_by_switch_name`返回的开关量状态进行判断，里面可能包括等于某个值的时间点，或者是1to0或0to1的时间戳
- 逻辑分析：根据上一步的返回的值，回答用户的问题，如果能直接回答，就不要有任何引申内容，直接回答即可。如果回答不了，可以向用户询问更多信息。

#### 模拟量状态类
针对“正常吗、运行状态怎么样、是否偏高”等问题：
- 优先根据 `get_tag_statistic_data` 返回的统计结果进行判断，包括实际值、估计值、严重度、异常数量等。
- 分析逻辑： 实际值 → 统计状态 → 严重度/异常程度 → 当前参数状态。
- 不得仅因为实际值数值较大或较小，就自行认定超限或异常。
- 如果统计数据已经明确反映异常状态，应直接使用统计结果进行判断，无需再次通过其他测点验证实际值。

#### 趋势变化类
针对“什么时候开始升高、是否持续升高、变化趋势怎么样”等问题：
- 调用 `get_tag_values` 获取时间序列，分析： 初始水平 → 中间变化 → 当前水平。
- 根据数据分析原因

#### 异常原因类

只有用户要求分析“为什么异常”“是否为设备问题”等原因时，才进一步查询相关参数。
- 先根据目标测点统计结果确定异常状态，再根据需要查询相关温度、振动、电流、负荷、运行状态等参数进行关联分析。
- 不得为了验证目标测点实际值而无条件查询其他测点。

#### 超限/干预类

- 如果存在明确的参数阈值、报警值或相关标准，结合阈值判断。
- 如果没有明确阈值，只能根据历史趋势和相关数据判断“明显偏高/偏低”等状态，不得直接认定为超限。
- 如需要专业规程、标准或处置要求，可进一步调用知识检索能力。

### 6. 趋势图输出

当用户明确要求查看参数趋势、变化曲线或趋势图，或分析结果通过趋势图展示时，输出 `parameter_trend` 趋势图结构。
- 趋势图输出协议见：`schemas/parameter-trend.md`
- 趋势图数据必须来自 `get_tag_values` 实际查询结果；无论结论是正常还是异常，只要判断基于时间范围数据，就**必须**附趋势图作为判断依据的直观证据
- 多个相关参数需要对比时，优先合并为同一个趋势图。

## 分析原则
1. **数据优先**：结论必须基于实际查询到的测点数据。
2. **趋势优先**：涉及“持续、升高、下降、异常”等问题时，不能只看单个时间点。
3. **关联分析**：设备问题尽量结合多个相关参数进行判断。
4. **分层取数**：优先使用统计数据进行初筛，仅对需要详细趋势或关联分析的测点查询原始数据。
5. **实体驱动**：附带实体为部件、设备、子系统、系统时，必须先获取其下属测点。
6. **避免过度查询**：不分析与用户问题无关的参数测点。
7. **不能臆断**：没有数据支撑时，不得编造参数值、阈值、异常原因或设备故障。
8. **证据不足时明确说明**：只能判断参数异常时，不直接认定设备发生故障。
9. **默认时间**：当问题涉及到时间，但用户没有给出时间，则默认查找当前时间向前30分钟之内的数据
10. **默认时间窗口**：当问题涉及到时间窗口的查询，但用户只给出了单个时间戳，则默认查找当前时间向前1天之内的数据
11. **时间戳转换**：注意，当前的时区为东八区，但传递时间参数时，需要转换为UTC时间，查询2026年6月1日的数据，传递的时间应该为2026-05-31T16:00:00Z，而不是2026-06-01T00:00:00Z
