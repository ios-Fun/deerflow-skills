# 异常原因与故障诊断

## 适用场景
- 用户询问"为什么异常"
- 用户询问"是否为设备问题"
- 用户要求确认具体故障模式

## 执行流程
必须严格按照流程顺序执行

### 1. 数据校验（最关键）
首先，先以 **5 分钟间隔**，时间区间为**用户输入时间点前后一小时**调用调用 `get_tag_values`或`get_last_time_by_switch_name` 查看用户输入测点的变化情况是不是真如用户所说的情况发展
如果不是，直接指出错误，不再执行后续流程

### 2. 获取故障模式图谱
必须调用 `default_graph_detail`，参数仅使用 `tag_list`，传入当前测点的 id。
获取该测点可能触发的故障模式及关键特征，该方法可以获取到与当前测点强相关的其他测点，将这些测点纳入后e续数据异动的考量范围。
如果没有查到故障模式，则以经验做可能性推断，不要再调用任何工具进行数据查验，直接输出结果。

注意：
- **每个特征下最多选取一个测点进行工具调用**，不得调用多个测点表征同一特征。

### 3. 时序数据验证
- 以 **5 分钟间隔**，时间区间为**用户输入时间点前后一小时**，调用 `get_tag_values`或`get_last_time_by_switch_name`。
- 查看当前测点时序是否满足某种故障模式的触发链路。
- 如触发链路需要其他测点数据，可查询其他测点。
- 每个测点只进行一次时序数据的查询，不要查询任何和该故障模式推导图无关的测点。
- 查询一轮后就直接整理结果，不要调用额外的工具再去校验数据。
- 不得查询与触发链路无关的测点数据。

### 3. 判断结论
- 满足故障模式触发链路 → 输出分析结果。
- 不满足 → 直接说明原因。
- 有初步结论就告知用户，用户追问再继续深入分析。

## 输出要求
用户要求确认故障时，明确回答：

| 结论 | 含义 |
|------|------|
| **可确认** | 关键特征全部满足 |
| **疑似** | 关键特征部分满足 |
| **证据不足** | 关键特征大部分缺失或数据不足 |

需列出该模式关键特征满足几项、缺几项。

## 注意事项
- 不得为了验证目标测点实际值而无条件查询其他测点。
- 只允许查询目标设备本身及其直接挂载测点，禁止跨设备查询。
- 不满足任何故障模式时，只给出"参数异常，暂无法确认具体设备故障"的阶段性结论。
